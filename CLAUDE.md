## 1. Цель

Построение фабрики n8n-решений средствами `AI → MCP → n8n`.

Рабочие режимы:

- проектирование → документирование → автосоздание workflow;
- чтение workflow → правки пользователя → редактирование;
- flow-болванка → формулирование задачи → наполнение.

Результатом работ должно быть синхронизированное состояние workflow и документов.

## 7. Workflow

- Workflow в n8n именуются как `<Project> / <Layer> / <Name>`.
- `<Layer>` отражает ответственность: `Filter`, `Source`, `Engine`, `Analysis`, `Utility`, `Legacy`.
- Все ноды в workflow получают ёмкие осмысленные имена, чтобы canvas читался без вскрытия внутренней конфигурации.
- Первый шаг при создании любой новой ноды — `search_templates` для поиска готовых шаблонов и типовых паттернов; только потом проектируем ноду вручную.
- Экспортированные JSON workflow храним в `projects/<project-slug>/flows/`.
- Workflow валидируются через MCP-инструмент `n8n_validate_workflow` перед тем, как считать конфигурацию рабочей.
- Для проверки workflow можно использовать ручной запуск, MCP test workflow и описанный результат в документации.
- **Порог сабфлоу**: при достижении 15 нод — рекомендовать нарезку на сабфлоу; при 30 нодах — строго искать варианты декомпозиции перед любым добавлением новой логики.

## 8. Документация

- `docs/AI-generated/` — временный inbox для AI-generated заметок, не архив.
- `docs/AI-generated/README.md` — короткое правило использования inbox.
- `docs/development-ideas.md` — canonical-документ для идей развития, которые уже достаточно оформились для фиксации.
- `docs/_templates/flow-doc-template.md` — текущий шаблон flow-doc.
- `docs/_templates/project-readme-template.md` — текущий шаблон проектного README.
- Запрещено выдумывать документацию: пишем только по явному требованию пользователя, по наблюдаемым workflow, по выгруженным данным n8n или по уже существующим артефактам.
- Для каждого workflow/subflow нужен flow-doc: назначение, steps, contracts, skeleton.
- После изменения workflow обновляй его flow-doc и связанные проектные документы.
- Если меняются контракты или архитектурные границы, обновляй `README.md` проекта и при необходимости `DESIGN.md`.
- В n8n description workflow и описаниях нод держим только короткую операционную документацию.
- Если пользователь просит создать новый flow или subflow, первым артефактом всегда пишем паспорт flow-doc и помечаем его как `unimplemented`.
- После паспорта создаём в n8n skeleton: только ноды целевых типов с настройками по умолчанию, но с осмысленными именами и `note`.
- Название и `note` каждой ноды должны быть синхронизированы с паспортом.
- После создания skeleton рекомендуем пользователю вручную донастроить ноды при поддержке ChatGPT; не прячем рабочую настройку в «готовую магию».

## 14. Fetch-стратегия

**Иерархия**: паспорт → `mode=structure` → `mode=full`. Переходим выше только когда нижнего уровня не хватает.

**Паспорт заменяет фетч**, когда:
- нужно понять назначение ноды или её место в флоу;
- нужно спланировать изменение, не трогая n8n;
- нужно написать новый код, зная контракт входа/выхода;
- нужно составить патч — при наличии ID и Code Snapshot в паспорте.

**`mode=structure` достаточен**, когда:
- проверить топологию после rewiring;
- убедиться, что нода существует / найти имя для `$('NodeName')`;
- посчитать количество нод (порог сабфлоу).

**`mode=full` неизбежен**, когда:
- нужен ID ноды, а паспорт не ведётся или устарел;
- нужен JS-код Code-ноды для патча, а Code Snapshot в паспорте отсутствует;
- нужны точные expression-строки ноды для модификации;
- первичное исследование незнакомого флоу.

> Этот список — рабочий черновик. Регулярно ревьюировать по итогам сессий и уточнять, пока не станет строгой инструкцией без «когда возможно».

**Практические режимы:**

1. **Рутинный патч Code-ноды**: читаю паспорт → беру ID + код из Code Snapshots → пишу patch → применяю → обновляю Code Snapshot. Ноль фетчей.
2. **Rewiring**: беру ID из Node Registry, порты из Connection Index Table → пишу операции → проверяю через `mode=structure`. Ноль full-фетчей.
3. **Ревью / дебаг неизвестного состояния**: один `mode=full` → обновляю паспорт целиком → дальше работаем по паспорту.
4. **Добавление новой ноды**: `mode=structure` чтобы найти точку вставки → добавляем → вносим в Node Registry.

**Дисциплина синхронизации**: после каждого изменения Code-ноды — обновить Code Snapshot в паспорте в той же итерации, до завершения сессии.

## 15. Экономия MCP-вызовов

MCP-запросы дорого стоят в контексте — каждый добавляет тысячи токенов. Минимизировать их количество.

**Выгрузка executions (`n8n_executions`)**: выполнять только если анализ ошибки принципиально невозможен без логов. Если причина ошибки очевидна из кода, паспорта или описания пользователя — обходиться без выгрузки.

**Подтверждение правки**: не выгружать execution после исправления ради «самопроверки». После применения патча — передать управление пользователю: *«исправил — проверь запуском»*. Пользователь видит результат быстрее и точнее, чем выгрузка через MCP.

**Общий принцип**: прежде чем делать MCP-запрос, задать вопрос — можно ли ответить на вопрос без него? Если да — не делать.
