# Инженерная практика работы с n8n

Дата: 2026-04-29. Статус: **current design** — рабочая модель пространства `lab-n8n`. Если `CLAUDE.md` фиксирует правила поведения агента, то этот документ фиксирует устройство практики: как мы раскладываем n8n-проекты, документы, workflow и будущие расширения.

Центральная тема: как работать в n8n так, чтобы результаты были предсказуемыми, воспроизводимыми, документированными, наблюдаемыми и пригодными для повторного использования.

## 1. Цели

1. Ввести общий словарь для будущих агентов и инженеров.
2. Зафиксировать структуру отдельных n8n-проектов.
3. Описать жизненный цикл workflow от черновика до рабочего состояния.
4. Определить границы документации и временных AI-generated заметок.
5. Задать строгую рекомендацию по наблюдаемости для active-проектов.

## 2. Терминология

**Project (проект)** — отдельная доменная единица работы: например, `job-searcher`, `pomodoro-logging`, `greenhouse-token-check`. У проекта есть свои workflow, документы, контракты и, когда нужно, dashboard.

**Flow (флоу)** — самостоятельный workflow n8n с собственным trigger. Это точка входа в сценарий.

**Subflow (сабфлоу)** — workflow, вызываемый из другого workflow через `Execute Workflow`. Он используется как переиспользуемая логика внутри проекта или между проектами.

**Contour (контур)** — инстанс n8n с отдельной БД, адресом и жизненным циклом. Сейчас рабочий контур один: `prod`.

**Flow-doc** — паспорт конкретного workflow/subflow: назначение, шаги, контракты и mermaid-skeleton.

## 3. Структура

Главная интенция структуры — сделать n8n-проекты отдельными разделами. Каждый проект должен читаться как самостоятельный инженерный артефакт, а не как набор разрозненных workflow.

Целевая структура:

```text
lab-n8n/
├── AGENTS.md
├── CLAUDE.md
├── DESIGN.md
├── changelog.md
├── docs/
│   ├── AI-generated/
│   │   └── README.md
│   ├── _templates/
├── projects/
│   └── <project-slug>/
│       ├── README.md
│       ├── flow-docs/
│       └── flows/
└── scripts/
```

Существующие проектные артефакты постепенно приводятся к этой структуре. Новый проект создаётся сразу в `projects/<project-slug>/`.

Минимальный проектный раздел:

- `README.md` — карта проекта, архитектура, контракты, dashboard-заметки и индекс flow-doc.
- `flow-docs/` — паспорта workflow/subflow или индекс на них во время миграции.
- `flows/` — экспортированные JSON workflow, когда проект переехал в новую структуру.

## 4. Документы и AI-generated

`docs/AI-generated/` — короткий временный inbox для заметок, созданных агентами. Это не архив и не canonical storage.

Если AI-generated документ становится полезным, его надо перенести в проектный раздел, `DESIGN.md` или другой явный canonical-документ. Мусорные черновики удаляются.

`docs/AI-generated/README.md` кратко фиксирует это правило и не обязан индексировать удалённые черновики.

## 5. Жизненный цикл workflow

Рабочий цикл: `idea → passport(unimplemented) → draft/skeleton → validate → check → document → sync`.

- **Idea** — задача сформулирована на естественном языке.
- **Passport** — flow-doc создан до реализации, зафиксированы назначение, шаги, контракты и skeleton; статус документа `unimplemented`.
- **Draft / Skeleton** — workflow создан в n8n как болванка на нодах целевых типов с настройками по умолчанию, но с осмысленными именами и `note`, синхронизированными с паспортом.
- **Validate** — workflow проверен через `n8n_validate_workflow`, явные ошибки конфигурации устранены.
- **Check** — сценарий прогнан вручную или через MCP-тестовый запуск; результат понятен инженеру.
- **Document** — обновлён flow-doc, проектный README и контракты на границах.
- **Sync** — локальные JSON/docs соответствуют текущему canvas в n8n.

## 6. Правила жизни проекта

`project-slug` — `kebab-case`, короткий и уникальный.

Проекты независимы по умолчанию. Общую логику не выделяем заранее; место для неё появится только по реальному кейсу.

У проекта есть статус: `draft | active | archived`. Статус фиксируется в начале `README.md` проекта.

Workflow в n8n именуются как `<Project> / <Layer> / <Name>`, где `<Layer>` отражает ответственность: `Filter`, `Source`, `Engine`, `Analysis`, `Utility`, `Legacy`.

Каждый workflow и subflow должен иметь осмысленные имена нод, чтобы canvas читался без вскрытия каждой конфигурации.
При создании любой новой ноды сначала ищем шаблоны через `search_templates`, затем проектируем ноду как целевой skeleton с умышленным именем и `note`.

## 7. Расширения и сервисы

Конкретику по внешним сервисам пока не фиксируем. Когда появится реальный кейс, отдельно решим:

- где живёт код сервиса;
- кто отвечает за деплой;
- как сервис подключается к n8n;
- какие контракты и тесты нужны на границе.

До этого `lab-n8n` не берёт на себя инфраструктурные изменения. Всё, что требует Caddy, compose, домены, секреты или VM-level деплой, эскалируется в `lab-infra`.

## 8. Наблюдаемость

Dashboard для active-проекта — строгая инженерная рекомендация, а не блокирующий trigger, DoD или условие активации.

Хороший dashboard проекта должен отвечать минимум на три вопроса:

1. Живы ли ключевые workflow.
2. Когда был последний успешный запуск.
3. Есть ли бизнес-сигналы, ради которых проект существует.

Конкретный шаблон dashboard и способ provisioning фиксируем позже, когда появится первый устойчивый per-project пример.

## 9. Документационные стандарты

- Пишем по-русски; технические термины вроде workflow, trigger, node, subflow можно оставлять на английском.
- Не выдумываем документацию. Project README и flow-doc наполняются только из пользовательского требования, наблюдаемого n8n workflow, выгрузки MCP или существующего canonical-артефакта.
- В проектных `README.md` держим карту, архитектуру, контракты, dashboard-заметки и ссылки.
- В flow-doc держим паспорт workflow: назначение, steps, contracts, skeleton.
- Если пользователь просит новый flow или subflow, паспорт пишется первым и получает статус `unimplemented`; только потом создаётся skeleton workflow с нодами-заменителями.
- Названия нод и их `note` синхронизируются с паспортом, чтобы canvas читался как рабочая схема, а не как набор технических автоимён.
- Кодировка: UTF-8 без BOM + LF.

### Canvas → паспорт

**Sticky-подложки как подзаголовки.** Если на canvas есть sticky-подложка под набором нод, её название становится подзаголовком в разделе Steps flow-doc. Node, лежащие на подложке, описываются внутри этого подзаголовка.

**Синхронность имён нод.** Имена нод в паспорте должны точно совпадать с именами нод на canvas. Перед написанием или обновлением flow-doc нодам на canvas присваиваются осмысленные названия — технические автоимена (`HTTP Request1`, `Code in JavaScript6` и т.п.) недопустимы.

**Mermaid skeleton.** Один Mermaid-блок = одна n8n node; `subgraph` = sticky-подложка. Skeleton должен максимально точно отражать canvas: порядок блоков, группировки и связи. Sticky note без исполняемых нод представляется пустым `subgraph`.
